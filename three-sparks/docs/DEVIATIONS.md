# What differs from upstream, and why

The serving stack is upstream's recipe at `7f1bd29` with the same checkpoint, draft, base image,
kernel revision, patch tree, TP3 + expert-parallel layout, FP8 KV, block size, index top-k, vision
settings and HAREM flags. Our short-prompt eight-stream rate reproduces upstream's published figure
(28.1 to 28.7 tok/s per stream here against about 28.4 there). The table below is the complete list
of deviations, grouped by whether they change what the engine does.

## Changes that affect scheduling or memory

| Setting | Upstream | Here | Why | Evidence |
|---|---|---|---|---|
| `--max-num-batched-tokens` | 2048 | **2304** (profiles v2 to v4) | Together with the threshold below, lets eight long prompts prefill in the same steps instead of one after another | [BENCHMARKS.md](BENCHMARKS.md) section 4, the scheduler A/B |
| `--long-prefill-token-threshold` | not set | **256** | Same | Same |
| `gpu-memory-utilization` | 0.88 in the example file; 0.80 in upstream's measured results | **0.80** | 0.88 left the head node under 2 GiB of free host memory during eight-way 500k prefill and the run was cancelled; upstream's own results doc runs at 0.80 with 12 to 13 GB free | [fair-v2 cancellation note](../results/long-context-500k-c8/fair-v2-cancellation-note.json), [SOURCE_MEMORY_REVIEW.md](private-notes/SOURCE_MEMORY_REVIEW.md) |
| `ENFORCE_EAGER` | 0 in the example file | **1** | Upstream's results doc states CUDA graphs are off in every measured configuration because vLLM sets `cudagraph_mode=NONE` for the FP8 draft cache on FlashInfer; the flag makes explicit what already happens. Measured cost upstream: 1.5 to 2 percent single-stream, inside noise | upstream docs/10 section 5.8 |
| `--limit-mm-per-prompt` video | 2 | 0 (v1 to v3), **2 from v4** | Upstream's repo omits the fixture clips its boot-time geometry gate reads, so the gate could only be skipped. We generated fixtures, ran the gate, then enabled video | [VIDEO.md](VIDEO.md) |

## Changes forced by what upstream did not publish, or by this hardware

| Item | Upstream | Here |
|---|---|---|
| Serving image | `docker/Dockerfile.gb10v8`, referenced but never published | [`prep/Dockerfile.serve-reconstructed`](../prep/Dockerfile.serve-reconstructed) from the kernel repo's tracked sparse-MLA Dockerfile, plus a bounded wheel build with a dependency fix after the first attempt failed. Image `sha256:af1cd749…` |
| GPU access | `docker run --gpus all` | CDI device injection, `--device nvidia.com/gpu=all` (`GPU_MODE=cdi` in the launcher, `legacy` restores upstream). These Sparks had no NVIDIA Docker runtime registered and registering one would have restarted dockerd under a live model |
| API exposure | binds all interfaces, no authentication | all-route bearer-token ASGI middleware; only `GET/HEAD /health` is public; the key is file-mounted and never in env or argv |
| Fast-load sidecar | `FASTLOAD_MODE=load` | empty (cold load). No sidecar for this image existed and one costs a dump boot plus 53 GB per node; boot is 250 to 260 s cold |
| Prelude tree | `tracks/tp3/patches/` with the vision block as a paste-in hook | flattened into `three-sparks/runtime/` with the hook and the xgrammar backport call inserted where upstream's README says they go |
| Video fixtures | not in the repository | two deterministic 4 s clips generated by `prep/video/make-video-fixtures.py`, installed under `runtime/fixtures/` |
| Memory settle gate | launcher prints a warning if 112 GiB is not reached | unchanged, but the operator checks memory explicitly before every switch |

## What is unchanged and easy to get wrong

- `index_topk` 8192, `CUDA_EXL3_PACKED_MAPPING`, `HAREM_VISION=1` and the whole `EXTRA_ENV` string
  are upstream's production configuration 13 values.
- `--mm-processor-kwargs {"max_pixels":12544000,"max_image_tokens":8000}` is upstream's; the second
  key is the video brake and the first is only read by vLLM's budget estimate.
- `reasoning_effort=low` and `clear_thinking=true` are upstream's defaults and every gate here used them.
